Consolidated from the supplied JCI Carmona functionality specification and the latest user-defined role, reporting, LOI, financial, and Project Chair rules.
1. Core System Rules
All registered users—including Admin, BOD, Treasurer, and General Member—can create and submit project proposals.
Any registered user can become Project Chair after the project is approved. Project Chair is a project-level assignment, not a permanent account role.
All authenticated users can view and monitor project information and project-level budget, fund, and expense information.
Project Chair authority is project-scoped and does not grant Treasurer financial-recording authority.
Treasurer is the only permanent role with authority to record and maintain project financial records, including transactions, expenses, disbursements, and liquidation.
Project Chair can prepare, upload, print, and download project reports and send them to Admin.
Treasurer can review liquidation and prepare the Overall Financial Report; Overall Financial Report preparation and maintenance are Treasurer-only.
Admin can view reports submitted by Project Chairs and Treasurer and can print/download submitted reports.
Frontend visibility and backend authorization must enforce the same permission model.

4. Project Monitoring System
All authenticated users can monitor project details and project-level financial information.
Monitoring does not automatically grant edit, approval, disbursement, financial-recording, or delete authority.
Project cards show title, status, Chair, date, progress, approved budget, used funds, remaining funds, and task count.
View Project is available to users with access; Manage Project appears only for users with project-scoped authority.
Monitoring includes Overview, Status, Progress, Tasks, Timeline/Milestones, Budget & Funds, Expenses according to access, LOI, Documents, and Reports.
Dashboard emphasizes active projects, approval attention, upcoming activities, task deadlines, budget/fund summary, and report status without duplicating source-module records.

10. Overall System Functionality & Logic
Authentication determines permanent organizational role and baseline access.
Project creation is available to all registered users.
Project approval is workflow-controlled and auditable.
Chair assignment occurs after approval and may select any registered user.
Chair controls are scoped by project ID and disappear when the assignment is removed/replaced.
Task permissions are project/task-scoped; assigned users can update their own tasks while the Chair manages tasks within chaired projects.
Financial permissions are separate from Chair permissions; only Treasurer retains permanent financial-recording authority.
All users can monitor projects and project-level funds/budgets.
Reports are uploaded/submitted by the responsible user; Admin receives and monitors submitted reports.
Overall Financial Report preparation/maintenance belongs to Treasurer; Admin receives/views submitted copies.
Required fields, dates, budget values, attachments, and workflow conditions are validated before submission.
Important workflow and financial actions are audit logged.
Frontend controls and backend/API authorization enforce the same rules.
Critical records should be archived/soft-deleted instead of destructively deleted.
11. Audit & Security Logic
Log create, update, submit, approve, return, reject, Chair assignment/reassignment, task assignment/reassignment, budget changes, expenses, report submission, archive, and soft-delete.
Store actor, timestamp, object/project ID, previous value where appropriate, new value, and remarks.
Prevent unauthorized direct API actions even when UI controls are hidden.
Preserve review history/comments for returned projects and preserve report/LOI versions where applicable.

13. Treasurer Ledger & Member Dues Management
The Treasurer Ledger is the central financial-recording module for transactions maintained by the Treasurer. It is separate from project monitoring and supports complete transaction history. The Treasurer also records monthly member dues for all registered users, while each member has a personal Member Dues view.
13.1 Treasurer Ledger
Treasurer is the primary and authorized recorder/maintainer of the Treasurer Ledger.
Record all applicable financial transactions with date, reference number, type, description, payee/payer, amount, project or account reference where applicable, supporting document, status, and remarks.
Ledger entries should support income/receipt, expense/payment, dues collection, disbursement, adjustment, and other configured transaction types.
Maintain a running transaction history with searchable and filterable records.
Link project-related transactions to the appropriate project when applicable.
Link member-dues receipts/payments to the specific registered member.
Support attachments such as receipts or supporting documents.
Allow Treasurer to review, correct, or update records according to authorization while preserving audit history.
Do not allow ordinary users to directly modify the Treasurer Ledger.
Critical financial records should use archive/void/soft-delete controls instead of destructive deletion.

14. Monthly Member Dues Module
The Member Dues module allows the Treasurer to record the monthly dues status of all registered users. It is connected to the member directory and Treasurer Ledger so that a dues payment can be reflected in both the member's dues history and the financial transaction record.
14.1 Treasurer Member Dues Functions
View all registered users who are subject to member dues.
Create/open a monthly dues period.
Record whether each member is Paid, Unpaid, Partially Paid, Overdue, Waived/Adjusted, or another configured status.
Record payment date and amount.
Record reference/receipt number.
Upload proof of payment where applicable.
Add remarks or adjustment reason.
Correct dues records with audit logging.
View monthly collection totals and outstanding dues.
Filter by month, member, status, and payment period.
Send a notification to the member when a dues payment is recorded or when a member remains unpaid/overdue.
Keep a historical record of each member's monthly dues.

Paid: amount paid meets the configured monthly dues amount.
Partial: amount paid is greater than zero but below the configured dues amount.
Unpaid: no payment has been recorded by the configured due-date logic.
Overdue: unpaid or partial after the configured due date.
Waived/Adjusted: an authorized adjustment has been recorded with a reason and audit trail.
Exact due amount, due date, grace period, and adjustment rules should be configurable by authorized administrators/financial governance and should not be hard-coded without chapter approval.
