1. System Overview and Core Principles
The JCI Carmona Online Project Management System is designed to support project ideation, review, approval, execution, financial monitoring, documentation, reporting, and member dues management in one organized role-based system. The revised workflow reduces unnecessary effort by requiring a short Project Concept Letter before a member prepares a complete Full Project Proposal.
All registered users — Admin, BOD, Treasurer, and General Member — may submit a Project Concept Letter and later develop a Full Project Proposal when endorsed.
Any registered user may become Project Chair only after final project approval. Project Chair is a project-level assignment, not a permanent account role.
All authenticated users may view and monitor authorized project information and project-level budget/fund information.
President review of the Project Concept Letter is an initial endorsement for development, not final authorization to implement the project.
Final project approval follows the chapter’s configured formal approval authority and review sequence.
Treasurer retains exclusive permanent authority to record and maintain official financial transactions, expenses, disbursements, liquidation, ledger records, and member dues.
Project Chair manages project execution and tasks for chaired projects but does not automatically gain Treasurer authority.
Important workflow, financial, assignment, and reporting actions are audit logged.
Frontend visibility and backend authorization must enforce the same permission model.
Recommended naming: Use “Project Concept Letter” for the internal initial project request addressed to the Chapter President. Reserve “Letter of Intent (LOI)” or “External Partner Letter” for communications with external partners, sponsors, LGUs, schools, organizations, or other collaborators.

2. Governance, Roles and Permission Model
Role / Assignment
Primary Responsibilities
Admin
System administration, member/account management, organization-wide project monitoring, workflow visibility, submitted-report monitoring, and authorized administrative oversight. Admin may also submit projects and may become Project Chair for an approved project.
BOD
Organization-wide project and budget monitoring, participation in configured formal project review/approval, member registration where authorized, and access to authorized reports.
Treasurer
Exclusive recorder/maintainer of official financial transactions, Treasurer Ledger, project financial records, liquidation review, budget/fund records, member dues, and Overall Financial Report.
General Member
Submit project concepts, develop proposals after endorsement, view projects and authorized financial information, view own member dues, and participate in assigned project tasks.
President / Reviewing Authority
Performs initial review of Project Concept Letters addressed to the Chapter President. May endorse a concept for full development, return it for revision, or decline it. Final project approval remains a separate formal stage unless chapter rules explicitly combine them.
Project Chair (dynamic)
Assigned after final project approval. Manages the approved project, tasks, milestones, schedule, project documents, external LOIs/partner letters, and project reports within the assigned project.

2.1 Core Permission Principles
Participation: Every registered user may initiate a project by preparing and submitting a Project Concept Letter.
Concept Review: President/reviewing authority may review the initial concept but this does not by itself activate implementation.
Proposal Development: Only endorsed concepts proceed to Full Project Proposal preparation.
Chair Assignment: Any registered user may be assigned Project Chair after final approval.
Monitoring: All authenticated users may monitor project information according to visibility rules.
Tasks: Chair manages tasks in chaired projects; assigned users update their own assigned tasks.
Finance: Treasurer alone records and maintains official financial records.
Reports: Project Chair handles project reports; Treasurer handles overall financial reporting.
Dues: Treasurer records member dues; each member may view only their own dues records unless another role has explicit governance authority.

6. Project Concept Letter and President Review
The Project Concept Letter is a short internal letter addressed to the Chapter President. It presents the proposed project idea and requests initial endorsement to proceed with detailed planning. It should be concise and should not require the proponent to complete the entire implementation plan before the concept receives initial confirmation.

7.2 Formal Review and Approval
Validate required proposal information before submission.
Route the Full Project Proposal to configured reviewers/approvers.
Allow financial/budget review where required.
Allow BOD or other formal approving authority review according to JCI Carmona governance.
Record Approve / Return for Revision / Not Approve decisions and comments.
Preserve all review history and resubmission history.
Final approval activates Chair assignment and implementation setup.

8. Project Chair and Task Management
Project Chair is assigned only after final project approval.
Any registered user may be assigned as Project Chair.
Chair authority is limited to projects where that user is currently assigned as Chair.
Chair may create, assign, reassign, prioritize, update, and monitor project tasks.
Assigned users may update their own task status, notes, and completion evidence.
Admin, BOD, Treasurer, and ordinary members may monitor task progress according to access but do not receive Chair-level management rights unless they are Chair for that project.
Chair may manage milestones, schedule, project documents, and project reports for chaired projects.
Chair cannot record official financial transactions merely because of Chair status.

9. LOI / External Partner Letter Logic
To avoid confusion with the internal Project Concept Letter, the system should use “External LOI / Partner Letter” for letters addressed to organizations outside the internal project approval workflow.
External LOI / Partner Letter remains linked to a project.
Project title, reference, approved description, applicable dates, and authorized project information may auto-populate.
User completes recipient, organization, purpose, requested collaboration, signatory details, and letter-specific content.
Versions must be preserved when a letter is revised.
Changes in linked project data should not silently overwrite a previously issued letter version.
Access to prepare/send letters should follow project status and configured authorization.

10. Project Monitoring System
All authenticated users may monitor project details and authorized project-level financial information.
Monitoring does not automatically grant edit, approval, disbursement, financial-recording, or deletion authority.
Project cards may show title, stage/status, Chair, date, progress, approved budget, used funds, remaining funds, task count, and next milestone.
Project monitoring tabs should include Overview, Status, Progress, Tasks, Timeline/Milestones, Budget & Funds, Expenses according to access, External LOI/Letters, Documents, and Reports.
Dashboard should surface only summaries and attention items; source records remain in their dedicated modules to avoid redundancy.

12. Treasurer Ledger and Monthly Member Dues
12.1 Treasurer Ledger
Treasurer Ledger is the authoritative transaction-recording area.
Record transaction date, reference number, type, description, payee/payer, amount, member/project reference when applicable, fund/category, payment method, attachment, status, remarks, recorder, and timestamp.
Support receipt/income, payment/expense, dues collection, disbursement, adjustment, and other configured transaction types.
Link project-related transactions to the appropriate project.
Link dues payments to the specific member and dues period.
Corrections must preserve audit history.
Ordinary users cannot directly modify the Treasurer Ledger.
12.2 Monthly Member Dues
Treasurer creates or opens a monthly dues period.
System lists registered members subject to dues.
Treasurer records amount, payment date, reference, receipt/proof, status, and remarks.
Recommended statuses: Paid, Unpaid, Partial, Overdue, Waived/Adjusted, or configured status.
A dues payment should create or link to a corresponding Treasurer Ledger transaction.
Member receives a notification when payment is recorded or remains unpaid/overdue according to policy.
Members view only their own official dues records.
Exact dues amount, due date, grace period, waiver, and adjustment rules must be configurable rather than hard-coded without chapter approval.

14.1 Audit and Security Logic
Log create, update, submit, endorse, return, decline, approve, reject, Chair assignment/reassignment, task assignment/reassignment, budget change, expense, dues update, report submission, archive, void, and soft-delete actions.
Store actor, timestamp, object/project ID, previous value where appropriate, new value, and remarks.
Prevent unauthorized direct API actions even when UI controls are hidden.
Preserve review comments/history for returned concepts and proposals.
Preserve report and external LOI/partner-letter versions.
Use server-side validation for workflow status transitions, dates, budget values, and permission checks.

18. UI/UX and Implementation Standards
Use a clean, modern, professional organization-system design aligned with JCI Carmona branding.
Use a light theme with purposeful JCI-aligned accent colors; avoid excessive blank white areas and decorative outlines.
Navigation should be compact, scrollable when needed, responsive, and clearly grouped by function.
Avoid duplicate modules and duplicate record entry. Reuse linked project data where appropriate.
Use clear status badges for Concept, Proposal, Approval, Ongoing, Completed, Dues, and Report states.
Use cards for project summaries but keep detailed records in source modules.
Use pie/bar charts only where they improve comprehension; avoid unnecessary charts.
Ensure responsive layouts for desktop, tablet, and mobile; avoid overlapping elements and fixed-width content.
Keep buttons/action labels explicit: Submit Concept, Endorse for Development, Return for Revision, Create Full Proposal, Submit for Approval, Approve Project, Assign Chair.
Display role/permission-sensitive actions only when the current user is authorized; enforce the same restrictions on the backend.
Use accessible typography, sufficient contrast, clear icons, and readable table layouts.
Use archive/soft-delete for critical historical records instead of destructive deletion.
